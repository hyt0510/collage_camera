# モニター配信を無料枠で止められる構成にする設計案

状態：ユーザー承認範囲の実装・検証完了。デプロイは未承認・未実施。

## 目的と合意事項

参加者は1日1,000人を想定する。スマホを表示したまま放置する場合と、意図的な再読み込み・API直接取得を想定する。無料枠を優先し、取得済み画像による演出と、新着の通信を分離する。

ユーザーは、スマホの自動更新を3分で停止し、ボタンで再開する体験と、配信用画像をFirebaseからVercel Blobへ移す方向に同意した。VercelはHobby。以下の具体値・変更範囲は設計者の提案であり、この設計の承認時に確定する。

会場の写真が散開・集結する演出と、スマホで同様の動きを再現する画像形式は後続のUI設計で扱う。今回の実装では現在の全体JPEGを維持し、費用を守る配信の土台と3分停止を先に完成させる。元のUI改善の目的は未完了として引き継ぐ。

## 現状

- 会場端末が読み込み済み画像から1280×720、最大200,000バイトのJPEGを作り、30秒ごとに認証付きPOSTで更新する。
- 参加者GETではStorageのメタデータと承認済み投稿を確認する。CDNの10秒キャッシュを外れるとFirebaseへアクセスするため、参加者の取得回数とFirebase費用が切り離されていない。
- 画像には90秒の鮮度期限があり、2026年11月1日23:59（日本時間）以降は画面・取得・更新を止める。
- 本番Vercelの `collage-camera` に、GET `/api/monitor-preview` をIPごとに3,000回／60秒で制限するルールを設定済み。これは入口の緩い制限で、総転送量の保証ではない。カウンターはリージョン単位である。
- 作業ツリーには他セッションの未コミット変更が多数ある。ローカル `.vercel/project.json` のprojectIdは古い。本番設定は専用の一時ディレクトリから操作済み。

## 比較した方式

| 方式 | 利点 | 残る問題 | 判断 |
|---|---|---|---|
| 現在のFirebase配信をキャッシュで補強 | 変更が小さい | キャッシュミス・多インスタンス・クエリ変更によりFirebaseの読み取りが増える | 採用しない |
| 公開Blobをスマホから直接読む | 配信経路が短く、Firebaseアクセスをなくせる | アプリAPIの公開終了判定を迂回してURLへ直接アクセスでき、削除・上書きの反映にも遅れがある | 採用しない |
| 非公開BlobをAPI経由で配る | GETからFirebaseを排除し、APIで期限・形式・容量を検証できる | API実行とBlob読み取りの無料枠を消費する。上限時には停止する | 推奨案 |

Blobへの移行自体はユーザー選択済み。非公開ストアとAPI経由配信は、既存の公開終了条件を保つための設計者提案。

## 配信構成

1. 投稿原本と承認状態は引き続きFirebaseに置く。画像合成は会場端末内で行う。
2. POST `/api/monitor-preview` は既存の運営認証を先に確認し、公開終了もFirebaseより先に判定する。未認証の参加者にはFirebase・Blobどちらも呼ばない。
3. 運営更新だけが承認済み投稿を確認し、配信枠を予約して非公開Blobを上書きする。共有ロックの中では `getApprovedSubmissions` の5秒キャッシュを使わず、`listApprovedSubmissions` でFirestoreの現在の承認状態を読む。別インスタンスの古いキャッシュから、失効済み作品を再公開しない。
4. GET `/api/monitor-preview` は非公開Blobだけを読む。Firestore・Firebase Storage・承認一覧への呼び出しを一切行わない。Blob障害や上限到達時にFirebaseへフォールバックしない。
5. 現在のJPEGレスポンス、ETag、最終更新時刻ヘッダーを保ち、通常の参加者向けCDNキャッシュは最大10秒とする。エラーは `no-store`。公開終了後はBlobを読む前に410を返す。

### Blobの内容と読み取り

専用の非公開Blobストアに、固定パスのJSONを1つ保存する。内容は形式バージョン、サーバー採番の更新時刻、JPEGのdata URL、JPEG本文のETagとする。更新時刻は、運営認証の確認後かつ共有ロック取得を含む非同期処理を開始する前に採番し、後から更新しない。個人識別子・原本URL・運営トークンは含めない。ブラウザーにはこのJSONやBlob認証情報を返さず、APIがJPEGへ復元して配る。

1回の更新を1回の `put` に収める。画像と別の管理用Blobを毎回書いて操作数を倍増させない。最大200,000バイトのJPEGはbase64で約267KBになり、JSONは300,000バイト以下に制限する。100KB程度のJPEGを目標にするが、画質を検証するまでは既存の200KB上限を維持する。

`@vercel/blob` の非公開読み取りを使う。既存の90秒鮮度と非表示反映を維持するため、読取は `useCache: false` とし、Blobの上書き伝播待ちに依存しない。API前段のCDNキャッシュで正常利用の取得をまとめる。SDKのバージョンと `get` の戻り値・例外は実装時に公式資料と型で確認する。

公開GETではクエリパラメーターを受け付けない。クエリ付きのリクエストはBlobより先に400で拒否し、無制限に別URLを作って内部読み取りさせない。ただしヘッダー変更・CDNの分散・コールドスタート等を完全に防ぐ仕組みとは見なさない。

## 運営更新の上限

最短間隔を60秒、イベント全体の予約回数を1,500回とする。8時間×2日なら通常更新は約960回。運営端末を24時間動かしても上限で新しい書き込みを止める。上限は同じHobby枠の他用途を含む完全な保証ではないため、専用ストア作成時に当該チームの既存利用量を確認する。

サーバーのメモリー変数やブラウザーのタイマーだけで上限を管理しない。Firestoreの既存 `settings` コレクションに `monitorPreviewBudget` ドキュメントを追加する案とする。イベント識別子は公開終了時刻に固定し、`reservedCount` と `lastReservedAt`、書き込み競合対策の `pendingId`・`pendingUntil` を永続化する。デプロイ・端末再起動でリセットしない。

既存の `withOperationLock` を運営更新と投稿の非表示・削除時のプレビュー失効で共有し、`monitor-preview-publish` のキーを使用する。ロック中にFirestoreトランザクションで時刻・上限を確認し、予約を増やしてから `put` する。失敗時にも予約回数を戻さず、障害・再試行による書き込み上限のすり抜けを防ぐ。予約不能ならBlobへ書かない。更新上限は参加者GETから利用しない。

共有ロックの5分期限切れや例外時の早期解放後も、古い外部書き込みを中止できたとは仮定しない。更新処理はサーバー側のタイムアウトとAbortSignalで短く制限し、保存直前にも90秒の鮮度を確認する。

予約時にランダムな `pendingId` と、その画像の更新時刻＋90秒の `pendingUntil` を永続化してから `put` する。書き込みが正常終了した後にだけ、自分の `pendingId` と一致する場合に限りトランザクションで保留状態を解除する。`put` のタイムアウト・例外・サーバー停止・解除処理失敗では保留を残す。新しい公開と非表示・削除によるBlob失効は、共有ロック内でこの保留期限も確認する。成否不明の書き込みがまだ有効になり得る間は操作を始めず、最大90秒後の再試行を案内する409を返す。外部処理が確実に止まったと判断して保留を早めに消す最適化は行わない。

したがって5秒でタイムアウトした書き込みが10秒後に完了しても、その間に非表示・失効の完了を利用者へ知らせることはない。保留期限後に非表示が完了し、さらに古い `put` が遅れて完了した場合、そのJSONの時刻は最初の処理開始時のままなので、GETは期限切れとして拒否する。新しい画像を古い期限切れBlobが上書きする一時的な表示停止は許容し、次の正常更新で復旧する。古い処理の再試行時に更新時刻を現在時刻へ付け直すことは禁止する。ロック期限より鮮度期限が短い関係と、早期解放時の保留をテストで固定する。

運営認証済みの異常な連続POSTはロック判定等のFirestore読み取りを消費し得る。今回の脅威モデルは運営秘密情報を持たない参加者であり、認証情報流出への対策を実現済みとは表現しない。

## 非表示・公開終了・障害

- 投稿の非表示・削除時は、共有ロックの中で固定パスの配信用Blobを `del` して失効させてから管理操作を成功とする。失効用JSONの上書きは使わない。公式料金上、削除操作は無料なので通常公開の1,500回には含めない。未生成・削除済みは失効成功と扱う。`setSubmissionStatus` と `deleteSubmission` の既存の処理順を読み、非表示時は投稿状態の変更と失効を同じ運営処理に組み込む。Blob失効失敗時は成功表示にしない。無料枠到達後に削除まで拒否された場合も、古い画像は90秒の期限でAPIから配信不能になる。
- 検証後・保存前の投稿状態競合も考慮し、公開用 `put` と投稿状態変更が同じロック順を守る。既存の一括削除・投稿単位のロックを外側、`monitor-preview-publish` を内側とする。公開処理は共有ロックだけを取得し、そこから投稿単位・一括削除ロックを取得しない。実装計画でも各呼び出し経路の順序を明記する。
- CDNと参加者の30秒ポーリングによる遅れは残る。通常利用中の非表示反映は従来同様、最大約40秒＋処理・通信時間が目安。取得済み・保存済み画像の回収は保証しない。
- 3分停止中の端末は新着・非表示の確認も停止する。最後の画像を残し、必ず「自動更新停止中／最終更新時刻」を表示する。これをライブ映像とは案内しない。再開時に取得できなければ以前の画像を消す。UI演出で長時間の写真表示を行う場合はこの制約を引き継ぐ。
- 90秒以上古い、未来時刻、未知形式、容量超過、Blob未生成は配信しない。期限内の更新で同じ画像だった場合も、サーバーの更新時刻とJPEGのETagは区別する。
- 公開終了はAPIとクライアントの両方で既存日時を適用する。Blobは非公開のためAPIを迂回して閲覧できない。終了後は画像の定期更新も停止する。保存物の終了後削除は閲覧停止と別の運用作業として明示する。
- Blobの上限到達・障害時は配信を停止し、Firebaseへ切り替えない。会場モニター自体は原本表示を継続できるが、参加者向けプレビューの停止を運営に表示する。

## スマホの3分停止

モニターを開いた時点から180秒を絶対時刻で管理する。更新は現在の30秒間隔を維持し、180秒ちょうど以降は新規取得を始めず、進行中の取得も中止する。

「新しい作品を見る」で利用者が明示的に再開したときだけ、新たな180秒を開始する。バックグラウンドからの復帰や再レンダーは期限を延長しない。モニタータブを再び開く・ページを再読み込みする行為は再開相当になり得るため、これを攻撃防御の上限として説明しない。

公開終了は3分停止より優先し、画像を消して再開ボタンも無効にする。テスト用DOM環境・React Testing Libraryは追加せず、時刻判定を純粋関数として検証し、既存のブラウザー手段で実動作を確認する。

## 費用と保証の範囲

HobbyのBlobは2026年10月27日確認時点で、転送10GB・Simple Operations 10,000・Advanced Operations 2,000・保存1GBの無料枠。超過分の支払いは発生せず、上限到達時にはBlobを利用できなくなる。枠は他用途と共有し、攻撃で正常利用分の枠が先に尽きることは防げない。

GETからFirebaseを呼ばないことはコードとテストで保証する。Vercel/Blobの利用量が無制限に増えないことはHobbyのサービス制限に依存する。無料のまま無制限の攻撃下でサービス継続する保証はしない。API実行・CDNリクエスト・内部転送も枠を消費するため、画像容量だけで無料と判断しない。

1,500回はアプリが予約するSDKの `put` 呼び出し数であり、BlobへのHTTP試行回数や請求対象操作数そのものではない。導入した `@vercel/blob` 2.8.2には内部再試行があり、通信障害時は1予約で複数のHTTP試行が発生し得る。無料枠が1,500予約より先に尽きた場合は配信を停止する。追加課金を防ぐ根拠はHobbyのサービス制限であり、予約回数だけからAdvanced Operationsの使用量を断定しない。

投稿・景品・会場の一覧取得・検閲は引き続きFirebase等を利用する。今回の移行でアプリ全体の費用を0円と保証することはない。

## 検証と完了条件

1. GETの正常・条件付き304・未生成・期限切れ・終了後・Blob上限／障害で、FirestoreとFirebase Storageが呼ばれないこと。
2. 認証前拒否、60秒間隔、1,500回上限、同時更新、予約失敗・Blob失敗、再起動後の永続上限と、非表示処理との競合を検証する。
3. 3分停止・途中の非表示／復帰・手動再開・終了日時の優先を、時刻テストと実際の画面で確認する。APIの変更は既存のJPEG契約を保つ。
4. `npm test`、変更対象のlint、型チェックを実行する。通常のVitest fork終了で `kill EPERM` が再発した場合は出力を報告し、`npm test -- --pool=threads` でも検証する。
5. 専用Blobで承認済みのテスト画像を使い、API経由の取得・90秒失効・直接URLの拒否・障害時の停止を確認する。本番へ大量リクエストする負荷試験は行わない。
